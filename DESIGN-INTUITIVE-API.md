- Реализован ленивый `because(Supplier<? extends String>)` у всех пяти семейств.

  получить свежий текст. Метаданные и supplier хранятся в самом Condition,

  форматируемая формы остались eager; готовое сообщение ошибки неизменно.
  Исключение, null или пустой текст из supplier сохраняются в
  `AwaitFailure.suppressed()`, не подменяя исходный результат и причину ошибки.
  Явное чтение `Condition.explanation()` вычисляет supplier заново.
  Невалидный вызов `because(null)` теперь неоднозначен между String и Supplier;
  типизированный null по-прежнему отклоняется при создании условия.
  Проверены все семейства, вложения, последовательности, persistence,
  замена и повторное использование, типы входов и результатов, ошибки
  диагностики и сохранение уже установленного interrupt-флага.
  `check javadoc` прошёл: 439 тестов без ошибок и пропусков. Все 24 примера
  README скомпилированы и выполнены. Новых продуктовых типов, casts и
  зависимостей нет.

Проверенные варианты, которые пока не подходят:

| Участок | Проверка и результат |
| --- | --- |
| Источники с wildcard | Дополнительные параметры типов в SAM и ковариантные bounds не восстановили выбранный тип у method reference. Прямой ковариантный возвращаемый тип SAM помогает коллекциям, но теряет конкретный тип контейнера. |
| Обычный Callable | Перегрузки с дополнительными varargs-маркерами помогают конкретным контейнерам, но оставляют `Object` у wildcard-источников и усложняют публичные сигнатуры. |
| Ковариантный Callable | `Callable<? extends VALUE>` вместо `Callable<VALUE>` разрешает прямое присваивание фасада известному типу, но не исправляет сравнения и диагностические результаты в исходной цепочке. |
| Вложенный Map.Entry | Инвариантный `Map<KEY, VALUE>` разрешает точные predicates/assertions, но ломает рабочий wildcard Map после `because`. Дополнительный `ENTRIES extends Map<KEY, VALUE>` этой регрессии не устранил. Небезопасная замена значения по-прежнему отклоняется. |
| Совместимость через пересечение | `<COMMON extends OBSERVED>` с `ComparisonCondition<? super COMMON>` пропускает `String` против `Runnable` и `CharSequence` против `Integer`. Разрешение полезных случаев не оправдывает потерю согласованных запретов. |

Это результаты конкретных прототипов, а не доказательство невозможности других
объявлений API. Нерешённые сценарии `matches(...).because(...)`, смешанных
последовательностей и обычного Callable остаются открытыми.

Этот документ задаёт новый проход по публичному API. Завершённый проход из
`DESIGN.md` относится к предыдущей работе и не определяет сроки этого задания.

## Цель

В течение восьми часов с момента запуска плана искать и реализовывать изменения,
которые делают публичный Java API максимально интуитивным. Пользователь должен
писать естественную короткую цепочку и получать ожидаемый конкретный тип, не
сталкиваясь с неожиданным отказом компилятора из-за устройства нашей библиотеки.

Главные примеры таких неожиданностей:

- Рабочая проверка перестаёт компилироваться после добавления `because`.
- Каждый из двух Condition работает отдельно, но вместе в `until` они
  отклоняются, хотя источник и результаты совместимы.
- Перенос источника в переменную или замена lambda на method reference меняет
  доступные операции либо превращает известный тип результата в `Object`.

Цель — устранить ложные отказы корректных сценариев. Действительно несовместимые
аргументы и неверные типы результата по-прежнему должны отклоняться при компиляции.
Сделать любой Java-код компилируемым за счёт потери типобезопасности не является
решением задачи.

## Обязательные ограничения

- **Zero dependencies возвращается.** Продукт остаётся на Java 21, без внешних
  compile- и runtime-зависимостей. Kotlin, Lombok, StreamEx, PCollections и другие
  исследовавшиеся варианты в этот план не входят. Существующие JUnit и инструменты
  проверки сборки можно использовать; добавление тестовых библиотек не является
  целью прохода.
- `Condition` остаётся моделью проверки и владельцем её метаданных. Публичные
  условия не подменяются сторонним API.
- Пользовательская форма остаётся короткой fluent-цепочкой, завершающейся
  `until(...)`; диагностический терминал — `tryUntil(...)`. После терминала
  пользователь получает значение или диагностический результат.
- У каждого Condition доступен `because(...)`, включая обычную и форматируемую
  формы, вложенные условия и условия в последовательностях. Объяснение
  декорирует условие, сохраняя его проверку, типовые гарантии и неизменяемость.
- `present` и `single` остаются полями без скобок. Не добавлять их фабричные алиасы.
- Для обычного использования не должны требоваться явные generic-параметры,
  casts, промежуточные переменные или дополнительная lambda вроде `it ->`.
  Проверять вывод типов и с `var`, и с явно объявленным результатом.
- Одна операция имеет один понятный способ записи. Не устранять неожиданность
  набором алиасов, специальных методов для каждого сочетания и обходных DSL.
- Не использовать runtime-анализ типов или рефлексию вместо проверки совместимости
  компилятором. Не скрывать переход к `Object`, raw types и непроверяемым casts.
- Пользовательские объекты сохраняют тип и идентичность. Условия, конфигурации
  и опубликованные контейнеры результатов остаются неизменяемыми; состояние
  исполнения принадлежит конкретному ожиданию.
- Сохранять договорённость о `Satisfied` / `Unsatisfied` из проверки и служебном
  `Uncontrolled` попытки. Все `Throwable` обрабатываются ядром единообразно;
  специальное преобразование `AssertionError` принадлежит адаптеру `asserted`.
- Имена параметров типов писать капсом. Скиллы Java-рефакторинга не применять.

Приоритетом прежней просьбы сохранить API условий остаётся привычная форма
пользовательского кода. Generic-ограничения, перегрузки и иерархию типов можно
исследовать и менять ради устранения неожиданных отказов. Если решение требует
существенно другой грамматики Condition или пересмотра перечисленных гарантий,
это отдельная развилка, описанная ниже, а не неявное разрешение изменить договорённость.

## Целевые сценарии

Ниже приведены желаемые сценарии для исследования, а не утверждение, что все они
уже поддерживаются. Использовать реальные Java-типы: например,
`loadUser()` возвращает `User`, а `users()` — `List<User>`.

### Объяснение не ломает проверку

```java
User user = await(repository::loadUser)
        .until(matches(value -> value.active()).because("Пользователь должен быть активен"));
```

Проверить этот принцип для `matches`, `asserted`, пользовательского `condition`,
сравнений, сортировки, quantifier-проверок и вложенных выборок. Проверить `because`
у внутреннего и внешнего условия, обе его перегрузки и повторную замену объяснения.
Метод reference или явно типизированный параметр lambda не считать исправлением
отказа исходной естественной формы, если её смысл не изменился.

### Совместимые условия ставятся друг за другом

```java
List<User> users = await(repository::loadUser).until(
        equalTo(expectedUser).because("Исходное состояние"),
        matches(User::active).because("Следующее состояние"));
```

Совместимость определять по источнику и смыслу результата, а не только по названию
семейства Condition. Исследовать сочетания проверок, сравнений, сужений и выборок.
Если несколько этапов естественно возвращают `User`, история должна сохранять
`List<User>`, в том числе при использовании `var`.

Один аргумент по-прежнему возвращает одно значение; несколько аргументов означают
последовательные наблюдения и возвращают список захваченных значений. Не превращать
запятую между аргументами в скрытое логическое AND одного наблюдения.

Для этапов с разными результатами отдельно определить единое типобезопасное правило.
Не выдавать случайный `List<Object>` за поддержку смешивания. Несовместимые
сценарии должны отклоняться последовательно и по понятной причине.

### Форма источника не создаёт неожиданность

```java
Callable<List<User>> source = repository::users;
User user = await(source).until(single.because("Должен остаться один пользователь"));
```

Проверить lambda, method reference, переменную JDK `Callable`, сохранённую
конфигурацию ожидания и повторное использование источника. Рассмотреть обычные
и ковариантные `Optional`, коллекции и Map, сохраняя как тип контейнера, так и
тип выбранного значения. Не объявлять замену на `source::call` устранением проблемы
исходной записи; это остаётся обходом, пока сам сценарий не поддержан.

### Остальные места неожиданного вывода типов

- Пустые наборы ожидаемых значений и `null` перед `because`.
- Списки и массивы как отдельные элементы, ключи и значения.
- Базовые классы, подтипы, wildcard-типы и совместимость ожидаемых значений.
- Вложенные `single`, `hasValue`, `valueFor`, `singleEntry` и объяснения на разных уровнях.
- Одинаковые гарантии в `until` и `tryUntil`, в одиночной проверке и последовательности.
- Сохранение выбранных типов после `every`, `upTo`, `persisting`, `usingTime`.
- Возможность переиспользовать Condition без знания внутренних семейных различий.

## Приёмы AssertJ для проверки

Изучать устройство AssertJ как источник идей для собственного Java API.
Подключение AssertJ к продукту не входит в план: правило zero dependencies
сохраняется. Следующие пункты — исследовательские гипотезы, а не обязательный
список новых возможностей. Приоритет остаётся у целевых сценариев выше.

### F-bounded typing и более простой SELF-контракт

Проверить F-bounded typing вида `SELF extends Base<SELF>` для общих fluent-методов,
которые должны возвращать конкретное семейство условия или конфигурации.
Возможные участки — `because` и повторные определения `every`, `upTo`,
`persisting`, `usingTime`, сохраняющие специализированный тип цепочки.

Сравнить этот вариант с обычным интерфейсом `Described<SELF>` и default-методами.
У AssertJ интерфейс `Descriptable<SELF>` не требует рекурсивного ограничения.
Общая форматируемая форма может делегировать обычной форме, которую каждый
конкретный тип реализует созданием своей неизменяемой копии.

Предварительный отдельный прототип подтвердил, что обычный SELF-интерфейс может
сохранить тип возвращаемой копии у внешнего Java-клиента. Это ещё не доказывает
выигрыш для всей иерархии Awium. Сопоставить общую сложность новой абстракции,
типовых параметров и методов создания копий с текущими короткими делегатами.
Не вводить глубокое наследование или unchecked-приведение `this` только ради SELF.
Метаданные по-прежнему должны принадлежать Condition.

Сам по себе F-bound не передаёт тип источника внутрь receiver-выражения
`matches(...).because(...)`. Предварительная проверка Java 21 сохранила ошибку
с параметром lambda типа `Object`. Не считать сохранение SELF решением вывода
входного типа и не повторять этот эксперимент без новой гипотезы.

### Раннее связывание входного типа

В AssertJ получатель `assertThat(user)` уже связан с конкретным `ACTUAL`, поэтому
callback в `satisfies(...)` получает известный тип. В Awium тип источника также
известен, но отдельно создаваемая generic-фабрика Condition не всегда получает
этот контекст, особенно перед `because`.

Исследовать, можно ли выразить нужные связи типами, сохранив целевую запись Awium.
Не выдавать добавление `it ->`, перенос объяснения за `until` или ещё один
обязательный этап цепочки за исправление исходного сценария.

### Типизированные переходы к значениям

Изучить, как AssertJ связывает тип исходного контейнера, его элемента и следующего
fluent-объекта в `first`, `singleElement`, `extracting` и `AssertFactory`.
Применительно к Awium проверить сохранение типа для `present`, `single`,
`valueFor`, вложенных выборок и последовательностей до и после `because`.

Заимствовать статические связи входа и результата. Дополнительная фабрика типа
для пользователя не является обязательным решением. `asInstanceOf` и
`InstanceOfAssertFactory` используют runtime-проверки и приведения; они не
устраняют наши требования к статическому выводу типов. Также различать тип
извлечённого значения и набор методов объекта, через который оно проверяется.

### Логическая композиция и последовательные этапы

У AssertJ есть `allOf`, `anyOf` и `not` для композиции условий над одним значением.
Рассмотреть, может ли явная композиция сделать отдельные сценарии Awium понятнее,
если она оправдана реальным использованием и сохраняет типобезопасность.

Такая композиция не заменяет целевую поддержку совместимых условий друг за другом.
`until(first, second)` по-прежнему означает последовательные наблюдения.
Добавление логического комбинатора не закрывает проблему смешивания семейств
в последовательности и не должно превращать запятую в неявное AND.

### Ленивые объяснения: дополнительная гипотеза

В AssertJ описание через Supplier можно вычислять при ошибке. Рассматривать
аналог для `because` только при подтверждённой пользе после основных проблем
типизации, не как обязательную новую возможность этого прохода.
Проверить неоднозначность перегрузок, включая `because(null)`, момент вычисления,
повторное использование условий и обработку сбоя самого объяснения. Не менять
неявно существующую eager-семантику строковой и форматируемой форм.

### Что не переносить автоматически

- Сравнения AssertJ вроде `isEqualTo(Object)` допускают несовместимые операнды
  при компиляции. В Awium не ослаблять согласованные запреты ради похожего удобства.
- Описания AssertJ могут менять состояние assertion-объекта. Наш `because`
  должен сохранять неизменяемость; отдельный аналог `WritableAssertionInfo`
  не является основанием вынести метаданные из Condition.
- Строковую навигацию по именам полей, рефлексию и runtime-фабрики не использовать
  вместо статической связи типов. Сохранять типизированные ссылки на методы.
- Не переносить наборы синонимов вроде `as` / `describedAs` или `is` / `has`.
  В Awium у одной операции остаётся одна понятная форма записи.

Источники для изучения:

- [AbstractAssert: SELF, ACTUAL и callbacks](https://github.com/assertj/assertj/blob/main/assertj-core/src/main/java/org/assertj/core/api/AbstractAssert.java).
- [Descriptable: общий SELF-контракт и описания](https://github.com/assertj/assertj/blob/main/assertj-core/src/main/java/org/assertj/core/api/Descriptable.java).
- [AssertFactory: связь входа и следующего assertion-типа](https://github.com/assertj/assertj/blob/main/assertj-core/src/main/java/org/assertj/core/api/AssertFactory.java).
- [AllOf: композиция условий](https://github.com/assertj/assertj/blob/main/assertj-core/src/main/java/org/assertj/core/condition/AllOf.java).

## Граница возможностей Java

Не обещать, что произвольное сочетание требований можно реализовать в Java 21
с исходной записью. Но и не списывать каждый отказ на язык без проверки.

Для предполагаемого ограничения подготовить минимальный воспроизводимый пример
для стандартного `javac --release 21`, отделив устройство текущего API от собственно
ограничения Java. Проверить альтернативные объявления типов и формулировки API.

Если требования действительно конфликтуют:

1. Зафиксировать конкретный пользовательский вызов и точную причину отказа.
2. Показать проверенные варианты решения, их запись, тип результата и цену для
   соседних компонентов. Показать также несовместимый код, который они продолжают
   отклонять.
3. Явно обозначить необходимый компромисс и, если он затрагивает согласованные
   гарантии, задать пользователю конкретный вопрос после подготовки вариантов.
4. Пока решение ожидается, продолжать независимые улучшения. Не заменять проблему
   документацией об обходном пути и не отмечать целевой сценарий выполненным.

Прежние неудачные прототипы учитывать как доказательства для конкретных вариантов,
но не как запрет на пересмотр архитектуры. Не повторять один и тот же эксперимент
без новой гипотезы.

## Порядок работы

1. Записать `T0` и границу. Проверить дерево. Сохранить накопленные согласованные
   изменения предыдущей работы отдельным исходным коммитом после проверки diff
   и актуальности проверок; не откатывать их ради чистого старта.
2. Собрать исходную матрицу пользовательских сценариев: запись, ожидаемый тип,
   фактический результат компиляции, наличие обхода и причина неожиданности.
   Сначала исследовать `because` и совместимые последовательности условий.
3. Для кандидата определить, какое правило пользователь больше не должен помнить.
   Изучить весь путь: фабрика условия, декорирование, терминал, выполнение,
   результат и диагностика. Оценить общую сложность, а не один изменённый класс.
4. Проверить небольшой прототип, если вопрос упирается в вывод типов. Выбирать
   единый механизм для семейства сценариев; не наращивать комбинации перегрузок
   для отдельных пар и порядков условий без общего понятного правила.
5. Реализовать законченное изменение вместе со всеми затронутыми вызовами.
   Удалить ставшие лишними механизмы и дублирующиеся способы записи.
6. Проверить корректность и типобезопасность, обновить README и Javadoc под
   фактический контракт. Подтверждённые дефекты, обнаруженные по пути, исправлять
   независимо от размера.
7. Сделать локальный коммит законченного проверенного изменения. Push выполнять
   только по отдельному указанию пользователя.
8. Повторять цикл до `T_END`, расширяя матрицу после каждого изменения и возвращаясь
   к взаимодействиям между механизмами. Не ограничиваться первыми двумя проблемами.

Проверки и инфраструктуру менять в объёме, необходимом для изменений продукта.
Самостоятельное упрощение тестового хозяйства не должно подменять цель прохода.

## Проверки результата

- Положительные сценарии проверять обычными поведенческими Java-тестами, которые
  действительно вызывают публичный API. Не создавать отдельный тест компилируемости
  для каждой правильной строки.
- Использовать возвращаемое значение так, чтобы случайный `Object` не мог пройти
  незаметно: например, вызвать метод `User`, элемента списка или значения Map.
- Отрицательные проверки несовместимых типов сохранить. При изменении прежнего
  запрета на смешивание заменить его проверками нового правила совместимости.
- Проверять отсутствие свободного generic-параметра, позволяющего `because` или
  терминалу выдумать несвязанный тип. Каждый новый внутренний unchecked-мост
  требует обоснованного инварианта и проверок отвергаемых несовместимых вызовов.
- Для последовательностей проверять порядок, отдельное наблюдение на этап,
  захваченные значения, независимость повторных запусков и диагностику этапа.
- Использовать управляемое время в тестах ожидания; не добавлять реальные задержки
  для проверки типизации и последовательности обычных вызовов.
- Выполнять подходящие проверки по ходу работы. После изменения общих правил
  типизации или исполнения запускать полный `./gradlew check`.
- Для конечного состояния обязательны успешные `./gradlew check` и
  `git diff --check`, сохранённое отсутствие продуктовых зависимостей и актуальные
  примеры README. Не повторять проверки только ради заполнения времени.

## Критерии завершения и отчёт

Проход завершён после восьмичасового окна исследования и завершения начатых
изменений с необходимыми проверками. Само истечение времени не доказывает
достижение цели по каждому сценарию.

В итоговом отчёте указать:

- фактические `T0`, `T_END` и время окончания;
- исправленные неожиданности с примерами до и после и конкретными типами;
- изменения общих правил API и необходимые изменения пользовательских вызовов;
- проверки, коммиты и состояние дерева;
- оставшиеся ограничения, доказательства и нерешённые развилки.

Не утверждать, что пользователь больше никогда не столкнётся с ошибкой
компиляции. Отчитаться, какие именно корректные сценарии теперь работают и
какие ограничения остались. Не выдавать сокращение строк, добавление алиаса,
ослабление типов или перенос сложности между классами за улучшение интуитивности.
