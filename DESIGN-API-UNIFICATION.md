## Цель

Пользователь знает несколько правил и применяет их ко всему API. Добавление
`because`, вложение условия или замена лямбды эквивалентным источником не должны
неожиданно лишать его доступных операций или точного возвращаемого типа.

Единообразие определяется смыслом операции и совместимостью типов, а не тем,
каким внутренним классом представлено условие.

Та же цель относится ко всему внутреннему API: одинаковые операции имеют
одинаковые контракты, жизненный цикл, правила владения состоянием и обработки
результата. Внешнее удобство и внутренняя простота рассматриваются вместе.

## Уже согласованные требования

- Короткая, линейно читаемая fluent-цепочка с понятным намерением ожидания.
  Основная форма — `await(source).until(condition)`.
- `until` завершает цепочку и возвращает значение. `tryUntil` предоставляет
  результат ожидания с диагностикой.
- Condition остаётся моделью условия. `because` вызывается на самом Condition.
- `present`, `single` и аналогичные константы используются без скобок.
- Нормальное использование не требует явных generic method arguments,
  приведений типов и промежуточных переменных ради компилятора.
- Результаты не расширяются к `Object` для обхода проблем типизации.
  Несовместимые типы должны отвергаться при компиляции.
- Не добавляем алиасы и параллельные способы сделать одно и то же.
- Java, zero dependencies. Публичный API можно менять без обратной совместимости.
- Для источников коллекций поддерживаем `Collection`, а ожидаемые наборы могут
  быть `Iterable`. Различие уже согласовано и не требует отдельной иерархии.
- Сложность должна уменьшаться во всём решении: публичном API, реализации и
  тестах. Перенос сложности из одного компонента в другой не является целью.

## Предлагаемые правила публичного API

Правила ниже приняты как цели прохода. Реализуемость сочетаний проверяется
прототипами; существенные изменения этих правил требуют обсуждения.

### 1. Декорирование Condition

Любой Condition поддерживает все формы `because`: строку, формат с аргументами
и ленивое объяснение. Декорирование не меняет вход, результат или допустимые
места использования условия.

Одинаково допустимы объяснения на внешнем и внутреннем условии:

```java
until(single(present.because("пользователь должен существовать"))
    .because("ожидается один пользователь"))
```

Требование относится и к пользовательским условиям, сравнениям, выборкам,
квантификаторам, проверкам типа и преобразованиям. Повторный `because` заменяет
объяснение неизменяемой копией; исходное условие сохраняется.

### 2. Вложение условий

Если вход внутреннего Condition совместим с выбранным значением, вложение
допустимо независимо от внутреннего семейства условия. Полиморфные константы
не должны иметь особых запретов относительно обычных фабрик.

Целевые примеры для обсуждения:

```java
await(optionalUsers).until(single(present))
await(userGroups).until(single(single))
await(optionalIndex).until(hasValue(valueFor("user")))
```

Для реализации принимается результат внутреннего Condition. Тогда
для `Collection<Optional<User>>` первый пример возвращает `User`,
для `Collection<Collection<User>>` второй тоже возвращает `User`.

### 3. Квантификаторы

`all`, `any`, `none` и аналоги для ключей, значений и записей Map принимают
совместимые Condition по одним правилам. `because` работает на обоих уровнях.

Квантификатор проверяет контейнер и возвращает исходный контейнер с его точным
типом. Это отличается от выборки по смыслу операции: результат внутреннего
условия не превращает `all` в преобразование коллекции.

### 4. Последовательности

Условия, которые допустимы по отдельности и возвращают один тип, можно
последовательно передать в `until` и `tryUntil`, включая сочетания проверок,
выборок и типизированных условий. Разные внутренние семейства не являются
основанием для запрета.

Предлагаемый пример для источника `User`:

```java
List<User> stages = await(source).until(
    matches(User::created).because("создан"),
    instanceOf(User.class).because("тип подтверждён"),
    matches(User::ready).because("готов"));
```

Сохраняем смысл последовательности: каждый этап ожидает состояние источника;
результат предыдущего этапа не подаётся на вход следующего. Один Condition
возвращает одно значение, несколько — список результатов этапов.

Сохраняем запрет смешивания разных типов результата, чтобы случайно не
получать `List<Object>`. Совпадение результатов при смешивании семейств, напротив,
должно разрешаться.

### 5. Формы источника

`Callable<T>`, ссылка на его `call` и лямбда с тем же объявленным результатом
предоставляют одинаковые условия, настройки и возвращаемые типы.

Отдельно проверяем конструкторы, generic method references и wildcard-источники.
Текущее размещение `await` по каталогам — реализация, а не доказательство
выполнения этого правила: несколько импортов всё ещё могут дать неоднозначность.

Обычный клиент использует одну согласованную схему импортов и не выбирает другой
каталог или адаптер только ради вывода типов конкретной цепочки.

### 6. Сохранение типа во всей цепочке

Добавление настроек ожидания или `because`, сохранение Condition в переменную,
вложение и последовательность не должны неожиданно менять известный тип.
Проверки сохраняют конкретный тип источника, выборки возвращают тип выбранного
результата, явные преобразования — объявленный тип результата.

Отдельные обязательные случаи: `var`, подтипы, wildcard captures, `null`, пустые
ожидаемые наборы и нетипизированная лямбда перед `because`.
Последняя сейчас остаётся ограничением; наличие F-bound не означает её решения.

### 7. Симметрия терминалов

Для каждой поддержанной комбинации источника и условий существуют одинаковые
правила в `until` и `tryUntil`: декорирование, вложение, последовательность,
тип успешного результата и диагностика. Различается способ получения итогового
результата ожидания.

### 8. Одиночные значения и наборы

Имя и аргументы различают один объект и набор ожиданий. Для коллекций и текста
используем `contains(value)` / `containsAll(iterable)` и `doesNotContain(value)` /
`doesNotContainAny(iterable)`. Для Map одиночные операции называются
`containsKey`, `containsValue`, `containsEntry`; наборы явно содержат `All` или
`Any` в имени. Одиночная запись задаётся парой ключа и значения, набор — Map.
Алиасы прежних имён не сохраняются.

## Предлагаемые правила внутреннего API

Эти правила проверяются на реальном коде вместе с правилами публичного API.

### 1. Контракты и ответственность

Одинаковые операции используют одинаковые понятия, имена, параметры и формы
результата. У каждого компонента понятна одна ответственность. Условия,
выполнение проверки, управление этапами и повторение ожидания имеют явные границы.
Различия сохраняются там, где различается смысл, а не история реализации.

### 2. Общий механизм выполнения

Совместимые условия и способы их композиции используют общие правила запуска,
завершения и передачи результата. Не поддерживаем параллельные реализации
одинаковых правил для разных семейств или терминалов. Общий механизм не должен
требовать множества флагов, проверок конкретных классов и специальных обходов.

### 3. Состояние и жизненный цикл

Для каждого состояния ясно, кто его создаёт, изменяет и завершает. Едины правила
ленивой инициализации и изоляции между ожиданиями и этапами; одинаковые сущности
не получают скрыто разный жизненный цикл. Неизменяемые определения отделены от
состояния выполнения. Учёт очередности принадлежит компоненту выполнения этапов.

### 4. Результаты и диагностика

Проверки явно возвращают satisfied или unsatisfied. Выброшенный Throwable
становится служебным uncontrolled на границе выполнения, без выделения отдельных
типов исключений. Причина, объяснение, ожидаемое значение и сведения о прогрессе
передаются по единым правилам через вложения, последовательности и терминалы.
Метаданные условия принадлежат Condition и не дублируются в отдельной модели.
Одиночный операнд остаётся одним значением в диагностике; набор представлен
снимком. Для положительной проверки используется Expected, для проверки
отсутствия или несовпадения — Unexpected.
Общие сведения об условии и ходе последовательности доступны у любой записи
попытки. Ошибка источника или ожидания сохраняет уже известный прогресс;
состояние переходов по-прежнему принадлежит выполнению последовательности.

### 5. Валидация и границы типов

Одинаковые ошибки входных аргументов обнаруживаются на одинаковом этапе и
объясняются одинаково. Совместимость типов сохраняется от публичного вызова до
внутреннего выполнения; расширение к Object не маскирует противоречия контрактов.
Внутренние приведения, если необходимы, ограничены одной проверяемой границей.

### 6. Удаление дублирования без роста сложности

Убираем повторяющиеся контракты, промежуточные обёртки и адаптеры, когда они
не выражают отдельную ответственность. Общий код извлекается только при
совпадении смысла операций. Проверяем последствия для всех затронутых компонентов
и тестов: сокращение одного класса не оправдывает усложнение остальных.

## Как принимать решения

Для каждого правила согласуем конкретные пользовательские примеры и их типы.
Затем проверяем реализуемость на небольшом прототипе, включая сочетания правил.
Только после этого выбираем общую модель и переносим её в продукт.

Для внутренних изменений сначала формулируем общее правило и находим места,
которые его дублируют или нарушают. Проверяем влияние на вызывающий код,
состояние, типы и диагностику. Не ограничиваемся косметическим совпадением имён.

Если комбинация не реализуется в выбранной форме Java API, обсуждаем изменение
общего правила или синтаксиса. Не объявляем проблему решённой за счёт `Object`,
runtime-анализа типов, обязательных casts или ещё одного частного обхода.

- Для изменений внутреннего API проверяем общие правила на всех затронутых

  поведение, не закрепляя случайную структуру внутренних классов.
- Отрицательные компиляционные тесты защищают от несовместимых типов.
