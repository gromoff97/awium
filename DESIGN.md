# Упрощение объектной модели

Решения по результатам проверки версии `e203afd`.
Реализованы OOP-1, OOP-2 и OOP-4. OOP-3 отложен: `Timing` сохраняется,
поскольку уменьшение числа типов не оправдывает спорный выигрыш в читаемости.

Цель: меньше сущностей и переходов между ними при сохранении возможностей,
понятности, поведения fluent API и проверки совместимости условий компилятором.
Количество типов само по себе не является основанием для удаления.

Исходная модель: 30 production Java-файлов без `module-info.java`, 71 объявленный
тип с учётом вложенных и локальных типов: 23 класса, 12 интерфейсов, 33 record,
3 enum. Production-код занимает 3550 строк, включая `module-info.java`.

## OOP-1. Объединить состояние и поведение форматирования ошибки

**Статус:** реализовано; полный `check` прошёл.

**Где:** [FailureMessageRenderer.java](src/main/java/io/github/gromoff97/awium/FailureMessageRenderer.java),
вложенный `Context` и методы `render`, `format`, `emergency`, `message`,
`timing`, `condition`, `sequence`, `reference`.

Ранее `Context` хранил исходные данные и промежуточные строки одного
форматирования. Семь статических методов внешнего класса получали этот объект
аргументом и работали с его полями. Состояние и использующее его поведение
были разделены между двумя классами.

**Реализация:** поля и методы `Context` перенесены в `FailureMessageRenderer`.
На одну ошибку создаётся один экземпляр форматировщика; использующие его
состояние методы стали методами экземпляра. Вложенный `Context` удалён.

**Сохранить:** кеш уже отформатированных значений, аварийное сообщение при
ошибке пользовательского `toString`, исходные причины и suppressed exceptions,
обработку прерывания и проброс фатальных ошибок. Форматировщик не должен стать
общим изменяемым singleton.

**Эффект:** на один объявленный класс и четыре строки
меньше. Количество объектов одного форматирования не уменьшается: экземпляр
форматировщика заменяет экземпляр `Context`. Исчезает передача контекста между
методами.

## OOP-2. Убрать вложенную сессию сохраняющего условия

**Статус:** реализовано; полный `check` прошёл.

**Где:** [ConditionDefinition.java](src/main/java/io/github/gromoff97/awium/ConditionDefinition.java),
метод `preservingSession()`.

Ранее метод создавал обычную `ConditionSession`, затем оборачивал её во вторую
`ConditionSession`. Внешняя сессия подменяла успешный результат исходным
наблюдаемым значением. Для одного выполнения возникали два объекта сессии
и два уровня ленивой инициализации и обработки вызова.

**Реализация:** callback из `evaluatorFactory` адаптируется внутри ленивой
фабрики одной сессии. Сама адаптация результата остаётся необходимой.

**Сохранить:** исходный объект наблюдения, независимость разных ожиданий и
стадий последовательности, ленивую инициализацию, проверки `null`, исходные
checked/unchecked исключения и флаг прерывания.

**Эффект:** на один объект `ConditionSession` меньше
при каждом вызове `preservingSession()`. Число типов не меняется, код становится
на две строки длиннее. Ускорение не измерялось и не является обоснованием.

## OOP-3. Удалить отдельную иерархию временных отметок

**Статус:** отложено по согласованному решению; не реализовано.
`AwaitAttempt.Timing` и его реализации сохраняются.

**Где:** [AwaitAttempt.java](src/main/java/io/github/gromoff97/awium/AwaitAttempt.java),
`Timing` и его records `BeforeRetrieval`, `BeforeObservation`, `AfterObservation`;
[ObservationEvaluator.java](src/main/java/io/github/gromoff97/awium/ObservationEvaluator.java),
[WaitEngine.java](src/main/java/io/github/gromoff97/awium/WaitEngine.java).

Стадия попытки уже определяет, какие отметки существуют. Отдельная иерархия
`Timing` повторяет это различие: каждому варианту `Outcome` соответствует
фиксированный вариант `Timing`. Независимого выбора здесь нет.

**Рассмотренный вариант:** хранить временные отметки непосредственно в соответствующих
records `Outcome`, удалить интерфейс `Timing` и три его реализации.

| Исход попытки | Его временные отметки |
| --- | --- |
| `WaitingFailed` | `startOffset`, `completionOffset` |
| `SourceRetrievalFailed` | `startOffset`, `retrievalOffset`, `completionOffset` |
| `SourceInterrupted` | Все четыре, включая `observationOffset` |
| `Evaluated` | Все четыре, включая `observationOffset` |

Общие `startOffset()` и `completionOffset()` остаются в интерфейсе `Outcome`.
Например, `attempt.outcome().timing().completionOffset()` сокращается до
`attempt.outcome().completionOffset()`.

**Сохранить:** все временные отметки, их тип `Duration`, точки чтения часов,
порядок проверок дедлайна, переполнение монотонных часов, валидацию обязательных
полей. Никаких отсутствующих отметок через `null` или условное значение `0`.
Доступность наблюдения определяется вариантом `Outcome`, а не значением
`observed`: наблюдение `null` остаётся полноценным наблюдением. Форматирование
ошибки использует варианты `Evaluated` и `SourceInterrupted` для этого различия.

**Цена:** конструкторы исходов получают больше аргументов; набор четырёх
временных полей повторяется в двух records. Создание `Evaluated` остаётся
в одном вспомогательном методе `ObservationEvaluator`; новая иерархия или
универсальный контейнер вместо удалённого `Timing` не нужны. Меняется публичный
API чтения и конструирования подробной истории попыток; fluent-вызовы
сохраняются. Совместимые псевдонимы для удалённых типов не добавляются.

**Почему отложено:** отдельный `Timing` сохраняет понятную группировку
временных данных. Более короткий доступ к отметкам не даёт однозначного
выигрыша относительно более длинных конструкторов и повторения полей.
Успешные тесты проверочного варианта подтверждают проверенное поведение,
но не улучшение понимания кода. Ради счётчика типов это изменение не делать.

**Эффект проверочного варианта:** минус четыре объявленных типа, минус один
объект временных отметок на сформированную попытку, минус 25 строк в сумме
по затронутым production-файлам. Отдельные `Duration` сохраняются.

## OOP-4. Удалить промежуточный RecordedWait

**Статус:** реализовано; полный `check` прошёл.

**Где:** [WaitEngine.java](src/main/java/io/github/gromoff97/awium/WaitEngine.java),
метод `recordedWaitFor()` и record `RecordedWait`;
[Await.java](src/main/java/io/github/gromoff97/awium/Await.java), `capture()`;
[FailureFactory.java](src/main/java/io/github/gromoff97/awium/FailureFactory.java),
`capture()`.

Ранее `RecordedWait` переносил `WaitCompletion` и историю из движка в
`FailureFactory.capture()`, где они сразу перекладывались в `AwaitResult`.
Собственного жизненного цикла или поведения, кроме копирования списка, у него
не было. При этом движок уже умел передавать попытки в `Consumer`.

**Реализация:** `Await.capture()` создаёт `AttemptHistory`, передаёт его
в существующий `WaitEngine.waitFor(source, evaluator, recorder)`, затем
передаёт завершение и снимок истории прямо в `FailureFactory.capture()`.
Перегрузка с recorder доступна внутри пакета. `recordedWaitFor` и `RecordedWait`
удалены без заменяющей обёртки.

Политика выбора истории оказывается рядом с терминалом: `tryUntil` собирает
историю, `until` продолжает работать без её накопления. Движок знает только
о получателе событий попыток.

**Сохранить:** ограничение истории, сжатие по идентичности пользовательских
значений, неизменяемость опубликованного списка, общее число попыток,
содержимое последней попытки. `AttemptHistory` и `AwaitResult` сохраняются.

**Цена:** `Await.capture()` начинает явно зависеть от `AttemptHistory`.
Это два дополнительных оператора в уже существующем методе терминала.

**Эффект:** минус один объявленный тип, минус один
промежуточный объект на завершившийся `tryUntil`, минус 13 production-строк.
Существующие тесты, вызывавшие `recordedWaitFor`, переведены на публичный
`tryUntil`; проверки истории и числа попыток сохранены.

## Рассмотренные варианты, не включённые в правки

- **Заменить `CollectionViewSource` и `MapViewSource` функциональными
  интерфейсами.** Изолированная компиляционная проверка показала регрессию:
  `await(() -> List.of("ready")).until(single)` и
  `await(() -> Map.of("ready", 1)).until(singleEntry)` получают неоднозначный
  выбор перегрузки `await`. Для map также теряется точный `Map.Entry<String,
  Integer>`. Удаление делегирующих records этим способом нарушает fluent API.
- **Объединить `ConditionResult`, `AwaitAttempt`, `WaitCompletion`,
  `AwaitResult`.** Они описывают разные события и границы. В частности,
  успешная проверка может завершить ожидание таймаутом. Их различия нельзя
  устранить простым удалением обёрток; `RecordedWait` проверен отдельно.
- **Свести семейства условий к `Condition<Object, Object>`.** Устраняет
  ограничения применимости и точность результата на этапе компиляции.
  В этом списке такой компромисс не допускается.

## Проверка реализации

На итоговом рабочем дереве выполнен `./gradlew check --no-daemon`:
**311 тестов в 42 классах прошли, ошибок и пропусков нет**. Проверены
компиляционные контракты fluent API, JAR и JPMS-модуль, временные отметки,
дедлайны и переполнение часов, прерывания, история, причины ошибок и снимки
сообщений. Компиляция использовала штатные `-Xlint:all,-serial -Werror`.

Тесты истории переведены с удалённого внутреннего метода на `tryUntil`;
проверки состава, неизменяемости, числа и сжатия попыток сохранены. Добавлена
проверка ленивой независимой инициализации `preservingFactory` и сохранения
исходного объекта наблюдения через оба терминала. Тесты времени не менялись.
Тесты не удалялись и не отключались; новые зависимости не добавлялись.

Числа строк и типов измерены по исходникам; результаты профилирования памяти
или производительности не заявляются.
