## Цель

На отдельной ветке от `main` провести содержательную работу:
исследовать всю кодовую базу, улучшать косметику продукта и продуктового кода,

элементы и исправлять любой доказанный дефект независимо от размера исправления.
Завершать её можно только после зафиксированной ниже временной границы
и выполнения остальных критериев завершения.

Приоритет — понятный, простой код и удобный для новичка fluent API.
Одна операция должна иметь один основной способ выражения: без параллельных
представлений одной проверки, названий-синонимов и совместимых алиасов.
Глубина исследования и упрощений не ограничивается локальными правками.
Количество правок, новых типов или коммитов не является целью.
Если кандидат не делает код понятнее или оказывается неактуальным,
его исключают из списка работ.

## Объём работы

Исследовать всю кодовую базу: публичный API, Java-код библиотеки, иерархию типов,
пакеты, границы ответственности, тесты и вспомогательный код сборки.
Не ограничивать глубину упрощений заранее. Перемещения, объединение и удаление
классов или интерфейсов и перестройка внутренних связей разрешены при конкретной
пользе для понятности, cohesion и уменьшения coupling.

Направления улучшений:

- понятные имена переменных, параметров, методов и типов, включая публичные;
- удаление лишних, повторных и неиспользуемых импортов;
- единообразные отступы, переносы, расположение импортов и компактные fluent-цепочки;
- упрощение выражений, методов и устройства реализации с сохранением возможностей;
- удаление переменных, обёрток, типов и слоёв, которые не добавляют смысла;
- устранение дублирования операций в публичном API и внутренних механизмах;
- удаление недостижимого кода, неиспользуемых приватных элементов и устаревших
  обычных комментариев после проверки их назначения;
- понятные тексты диагностики и устранение очевидных опечаток без изменения
  причин сбоя, исходных исключений и значимой информации;
- очистка тестов от дублирования и устаревших ожиданий с сохранением нужных проверок.

Каждое удаление обосновывается текущими вызовами, контрактами и проверками.
Отсутствие текстового совпадения само по себе не доказывает неиспользуемость
публичного API, отражаемого типа или ресурса.

Публичные типы, фабрики, сигнатуры и расположение кода можно менять.
Backward compatibility не является целью: не оставлять алиасы, deprecated
методы, адаптеры и дополнительные пути только ради старого способа вызова.

README и Javadoc не изменяются. Не сохранять дублирующий API ради старых примеров
в документации. Дизайн обновляется для учёта выполнения и согласованных решений.

Новые функции, зависимости, общие профили настроек, `onAttempt(...)`,
публикация не входят в объём. Изменение API существующей возможности не считается
новой функцией. Новые внутренние конструкции должны решать конкретную проблему
и упрощать код в целом; не вводить абстракции ради предполагаемого будущего.
Скиллы рефакторинга не использовать, согласно инструкции пользователя.

## Однозначный публичный API

`Condition` — единая модель проверки для терминальных методов.
Предикаты выражаются через `matches(...)`, assertions — через `asserted(...)`,
выбор результата — через `yields(...)`.

Согласованный выбор:

```java
await(source).until(matches(predicate));
await(source).until(matches(firstPredicate), matches(secondPredicate));
```

Прямые перегрузки `until(Predicate...)` и `tryUntil(Predicate...)`, включая
одиночные предикаты, удалить. Не оставлять их как более короткие альтернативы.
Удаление этих коротких форм явно согласовано при grilling;
остальные формы fluent-грамматики сохраняются по этому дизайну.

`matches(...)`, `asserted(...)` и `yields(...)` не являются синонимами:
у них различаются успешность, обработка assertions и выбор возвращаемого значения.
`until(...)` и `tryUntil(...)` также сохраняются как разные способы обработки сбоя.

Для одной операции оставлять одно название. Перегрузки под этим названием
допускаются для разных представлений входных данных, например отдельных элементов
и готовой коллекции, если не создают неоднозначности или сложности типизации.
Это не разрешение возвращать параллельные модели проверки.

Проверить каталоги на подобные пересечения, включая `contains(...)` /
`containsAll(...)` и `hasValue(value)` / `hasValue(equalTo(value))`.
Убирать именно дублирующие пути, сохраняя возможность самой проверки.
Похожее название или возможность выразить специализированное условие произвольным
предикатом сами по себе не делают разные операции алиасами.

## Сохраняемые контракты продукта

- Сохраняются `await(source).every(...).upTo(...).persisting(...).until(...)`,
  порядок настроек, правило последнего значения и короткие формы с учётом
  согласованного удаления прямых предикатов.
- Сохраняются проверки одиночного предиката через `matches(...)` и обе терминальные формы.
- `Condition` остаётся моделью; `present`, `single` и другие константы доступны без скобок.
- Несколько совместимых условий, включая `matches(...)`, означают последовательные состояния,
  отдельные наблюдения и результат в порядке этапов.
- Возвращаемые типы, ограничения совместимости условий и вывод типов не ослабляются.
- Источник не читается повторно ради результата; сохраняются идентичность
  наблюдений и результатов и существующие правила снимков ожидаемых данных.
- Сохраняются таймаут, persistence, выполнение в вызывающем потоке, обработка
  прерывания, fatal errors, исходных причин и suppressed исключений.
- Конфигурация и определения условий неизменяемы; рабочее состояние локально
  одному выполнению.
- Сохраняются Java 21, отсутствие runtime-зависимостей и скрытость реализации.

Косметические и структурные упрощения сохраняют корректное поведение и возможности;
согласованная переработка API меняет способ их выражения. Исправление доказанного
дефекта может менять ошибочное поведение; его причина и ожидаемый результат
фиксируются отдельно и подтверждаются проверкой.

## Рабочий цикл

1. Выбрать участок или механизм и прочитать его связанные вызовы и проверки.
2. Сформулировать конкретную проблему и пользу изменения.
3. Проверить актуальность: нет ли у существующей конструкции важного назначения.
4. Сделать минимальную законченную правку во всех затронутых местах.
5. Проверить diff и выполнить подходящие проверки.
6. Записать результат и перейти к следующему участку.

Глубокое упрощение разбивать на проверяемые шаги, сохраняя цельную конечную модель.
При сравнении вариантов оценивать понятность и число необходимых понятий,
а не только количество строк или классов.
Повторные проходы должны смотреть на новые участки или другие аспекты кода.
Не создавать искусственных правок и не повторять тесты без причины ради времени.

## Обнаруженные дефекты

Исправлять любой доказанный дефект. Размер, сложность и выход за границу T8
не являются основанием перенести его исправление в отдельную будущую задачу.
Неподтверждённое подозрение сначала исследовать; оно не является дефектом само по себе.

Для каждой находки:

1. Отделить дефект от необычного, но намеренного поведения.
2. Описать конкретный вход, фактический результат и ожидаемый результат.
3. Найти причину и связанные вызовы.
4. Добавить минимальную регрессионную проверку, если существующих недостаточно,
   и воспроизвести ошибку до исправления.
5. Исправить причину, сохранить валидацию и обработку ошибок.
6. Проверить исправление и связанные контракты.

Не снимать полезные проверки и не менять их ожидания только ради зелёной сборки.
Неактуальные или опровергнутые находки убирать из активного списка.
Если для спорного поведения требуется решение пользователя, описать вопрос
и продолжать независимые улучшения. До доказательства не менять поведение
на основании одного предположения.

## Проверки и сохранение результата

- При начале — `./gradlew check` для исходной версии.

  Для чистого форматирования или импортов не добавлять новые тесты.
